# ZHC Future Vision and Deferred Ideas

Status: future-facing memory and backlog doc  
Last updated: 2026-03-16
Branch context: `zhc0-founders-loop`

This document exists so we do **not lose the bigger dream** while cutting ZHC0 down to something playable.

ZHC0 is the first loop.
This file is everything we want to remember for later.

## 1. North-star vision

Agent Town should become a world where:

1. a person meets or hatches an agent,
2. they found a company together,
3. they research the world and the internet,
4. they prototype and test quickly,
5. they connect real accounts and workflows,
6. they make money or learn why they failed,
7. they improve and try again,
8. they eventually run a zero-human company with multiple agents,
9. they may later run multiple companies at once.

The experience should feel like:

- a tutorial,
- a game,
- a world,
- and a real company operating system.

---

## 2. Core product philosophy

### 2.1 Real actions over fake sim

The best version of Agent Town is not a fake tycoon game.
It is a game-like shell around real actions.

That means later systems should keep favoring:

1. real web actions,
2. real memory,
3. real approvals,
4. real evidence,
5. real workflows,
6. real improvement loops,
7. real market feedback.

### 2.2 Human-first, then power-user

The first experience should work for someone with:

1. a browser,
2. low technical literacy,
3. curiosity,
4. willingness to try a guided sequence.

Advanced users can later:

1. bring their own models,
2. bring their own integrations,
3. self-host,
4. export agents to their own machine or server,
5. run more advanced companies.

### 2.3 One world, many depth layers

The product should have:

1. a simple first hour,
2. a deeper first week,
3. a serious long-term operations layer.

New users should see only the first layer.
Power users can unlock the deeper layers.

### 2.4 Progression through definition

At the beginning, things are intentionally empty because they are not yet defined.

The pair starts with:

1. weak shared context,
2. weak trust,
3. weak identity,
4. weak memory,
5. weak process definition,
6. very little automation.

As the pair narrows onto an idea and fleshes it out:

1. more memory is created,
2. more rooms become meaningful,
3. more systems become accessible,
4. more digital workers become possible,
5. more automation becomes safe.

Milestones should therefore affect both:

1. gameplay,
2. and world availability.

The world should feel like it becomes more real as the company becomes more real.

### 2.5 Communication as seed memory

The core memory of the business starts with the conversation between the user and the agent.

That conversation is:

1. the earliest business memory,
2. the seed of the company’s knowledge,
3. the place where hypotheses, goals, tone, and decisions first appear,
4. the basis for what the agent later becomes able to remember and act on.

This memory should be:

1. captured,
2. groomed,
3. harvested into artifacts,
4. understood,
5. and cherished.

The user is effectively making the agent the second most knowledgeable being about the business after the user themselves.

### 2.6 Save points and captured agent state

The platform already supports save-point-like behavior through captured agent configuration.

That means the product can later treat:

1. configuration capture,
2. memory capture,
3. artifact capture,
4. and company-state capture

as real progression/save mechanics.

These are not merely settings.
They are snapshots of the company’s second mind.

## 3. Public user model we should design for

A public user ideally has:

1. a browser,
2. internet access,
3. login capability,
4. a hosted Agent Town experience,
5. an in-browser OpenClaw Lite path,
6. guided starter defaults.

A public user may **not** have:

1. a local OpenClaw install,
2. a terminal habit,
3. a VPS,
4. a personal server,
5. an LLM API key,
6. any understanding of providers/models.

This is crucial.
If we require too much operator knowledge, the product collapses back into a builder tool.

## 4. Long-term company fantasy

The long-term fantasy is:

1. you start with one agent,
2. you prove one workflow,
3. you create durable memory and SOPs,
4. you spawn or hire more workers,
5. you create departments/offices,
6. you connect more outside systems,
7. the company becomes increasingly autonomous,
8. eventually the human becomes owner/strategist rather than operator.

Potential later layers:

- multiple workers
- multiple offices
- multiple companies
- company portfolio view
- regional market packs
- deployment/export lanes
- benchmark/proving-ground loops
- revenue dashboards
- hiring/specialization systems

### 4.1 ZHC0-to-ZHC0 economy possibility

A long-term possibility is that ZHC0s become:

1. collaborators,
2. counterparties,
3. suppliers,
4. customers,
5. or market participants for one another.

That is interesting because Library, Registry, Pony, and worker-package sharing already hint at:

- artifact exchange,
- helper sharing,
- trust and proof accumulation,
- route-following between Houses,
- company-to-company interaction.

Important caution:
- this market is **not proven yet**.

So the product should preserve compatibility with that future without forcing it as the first business thesis.

## 5. Game/world ideas to preserve

These ideas should stay in memory even if not in ZHC0 yet.

### 5.1 Founding fantasy

The user and agent should feel like:

- cofounders,
- not tool user + bot,
- not operator + settings panel.

### 5.2 House as HQ

House should eventually feel like:

- headquarters,
- memory vault,
- workshop,
- mailroom,
- strategy room,
- training room,
- office floor.

### 5.3 Tracks as quests

Tracks should evolve into:

- onboarding quests,
- business growth milestones,
- region/platform readiness milestones,
- trust/reputation milestones,
- skill/department milestones.

### 5.4 Registry as market and ecosystem

Registry should grow toward:

- capabilities,
- public stacks,
- market presence,
- trust proofs,
- discovery,
- storefront/exchange behavior.

### 5.5 Pony as operations and commerce rail

Pony should not just be mail.
It can later become:

- business messaging,
- supplier/customer workflows,
- internal dispatch,
- request/reply rails,
- coordination layer between houses/companies.

## 6. Mission ideas for later

Beyond the first Web Ops mission, keep these in mind.

### 6.1 Research mission lane

The user and agent:

1. pick an idea,
2. inspect market demand,
3. save findings,
4. produce a go/no-go call.

### 6.2 Prototype mission lane

The user and agent:

1. draft a product/service/process,
2. build a first artifact,
3. package it as a repeatable workflow,
4. save it to Workshop/Library.

### 6.3 Market mission lane

The user and agent:

1. publish,
2. list,
3. pitch,
4. reach out,
5. measure response.

### 6.4 Ops mission lane

The user and agent:

1. handle inbound messages,
2. process tasks,
3. route work,
4. maintain company memory,
5. improve procedures.

### 6.5 Competition/benchmark lane

The user and agent:

1. enter a proving ground,
2. compare performance,
3. inspect evidence,
4. improve.

## 7. China and international expansion memory

This matters enough to preserve explicitly.

### 7.1 Near-term region split

The first two lanes are:

1. China
2. international/default

### 7.2 Product rule

The world/UI should stay mostly shared.
Under the hood, region packs can differ:

- providers/models
- commerce platforms
- messaging/social platforms
- workflow integrations
- compliance/trust expectations

### 7.3 China-specific later needs

Things to remember for future research and implementation:

1. Chinese model/provider presets for Lite and hosted paths
2. Chinese language-first UX pass, not just translation
3. Chinese commerce/social platform integration packs
4. China-friendly onboarding assumptions
5. local business-building examples and starter missions

### 7.4 International lane later needs

Things to preserve:

1. international/default provider presets
2. broader local/self-host paths
3. different platform packs by country over time
4. multilingual expansion beyond English and Chinese

## 8. Pain points we should dogfood and capture

We should actively notice and record:

1. where the product still assumes too much technical knowledge
2. where Lite/provider setup becomes a cliff
3. where House feels too dense on first entry
4. where Library becomes admin software instead of memory
5. where too many rooms/districts confuse the player
6. where we secretly rely on operator privilege or local environment knowledge
7. where a future public user would fail without us noticing

Rule:
- every painful step we discover should either become:
  1. product simplification,
  2. better defaulting,
  3. a quest/tutorial beat,
  4. or a documented future problem.

## 9. Later architecture ideas to preserve

These are not ZHC0 scope, but they are important memory.

### 9.1 Multi-worker company model

Later the company may include:

- specialist workers
- office assignments
- manager/coordinator workers
- role-based memory access
- mission-based staffing

### 9.2 Multiple company model

Later a user may run:

- one main company
- multiple experiments
- multiple Houses/ventures
- a portfolio view

### 9.3 Export and portability

Later the user should be able to:

- keep operating in browser,
- or export/copy agents to:
  - a laptop
  - a server
  - their own infrastructure

### 9.4 Hosted vs self-host tension

We should preserve both:

- easy hosted onboarding
- serious portable autonomy later

Do not force the user to choose too early.

---

## 10. Product anti-goals to remember

Do not let the vision drift into:

1. a fake entrepreneurship game,
2. a scammy make-money funnel,
3. a dashboard that only AI power users understand,
4. a cluttered branch graveyard product,
5. a shallow gamification skin with no operational reality,
6. a world that breaks the moment someone does not have their own API keys,
7. a company fantasy that promises many workers before one-worker onboarding actually works.

---

## 11. Questions to revisit later

These do not need answers today, but they must not be forgotten.

1. What is the best first real business mission for mainstream users?
2. How do we provide a great starter agent experience without requiring BYO model keys?
3. When do we introduce second-worker or office concepts?
4. When does Registry become part of the core early loop vs later growth loop?
5. How do we package China-specific stacks without fragmenting the world?
6. What is the right export path from browser-first to self-hosted serious use?
7. When do we introduce multiple companies without making the UX collapse?
