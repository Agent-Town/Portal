# ZHC Subsystem Benchmark Map

Status: subsystem-by-subsystem benchmark and divergence map  
Last updated: 2026-03-16
Branch: `zhc0-founders-loop`

This document answers two questions at once:

1. **What existing games or product patterns should each ZHC subsystem learn from?**
2. **Where does Agent Town diverge because the human-agent pair is building a real company, not a fictional one?**

## 1. Product framing

ZHC is not a normal tycoon and not a normal automation game.

It is better understood as:

> a game-shaped environment where a human and an AI agent go from strangers to cofounders, then from cofounders to operators of a real zero-human company.

That means the product must support a real progression:

1. start empty and undefined,
2. establish trust and identity,
3. discover an idea,
4. create memory,
5. open more rooms and capabilities,
6. automate more of the work,
7. connect to real external platforms,
8. eventually launch and operate a company.

In Agent Town, **milestones should change the world**.
That is the key design rule.

---

## 2. Progression law

The player does not begin with a fully formed company.

They begin with:

1. themselves,
2. an unfamiliar agent,
3. little or no shared context,
4. an empty or mostly undefined world.

As the pair works together:

- more shared memory is created,
- more identity is defined,
- more rooms become meaningful,
- more automation becomes possible,
- more artifacts become reusable,
- more of the company becomes real.

This is important:

> the world should unlock because the pair has become more real together.

Not because the user farmed arbitrary XP.

---

## 3. Core memory law

The earliest and most important company memory is the **conversation between the user and the agent**.

That conversation is:

- the first draft of the business,
- the first set of assumptions,
- the first market hypotheses,
- the first operating style,
- the first trust relationship.

This means House Library is not just a note vault.
It is the beginning of company memory.

And agent configuration snapshots are not just settings.
They are a kind of **save point** in the evolution of the company’s second mind.

So the product should treat these as precious:

1. conversation capture,
2. memory grooming,
3. artifact harvesting,
4. configuration snapshots,
5. replayable company state.

## 4. Subsystem map

## 4.1 `/start` — arrival and first promise

### Current Agent Town role
- front door
- login
- first framing of what Agent Town is
- the place where the first worker/agent path begins

### Best benchmarks
- **Game Dev Tycoon**
- **Game Dev Story**
- **while True: learn()**

### What to borrow
- immediate readability
- one strong first action
- quick momentum
- no unnecessary jargon
- outcome-first framing

### What Agent Town changes
Unlike those games, this is not just the start of a simulation.
It is the start of a real partnership.

So `/start` must communicate:
- you are entering a world,
- you are about to meet or hatch a real worker,
- this can lead to real products and money,
- but the first step is still approachable.

### Design rule
The player should feel:
- curiosity,
- momentum,
- safety.

Not:
- tool anxiety,
- provider anxiety,
- setup fatigue.

---

## 4.2 Brain / OpenClaw Lite — first worker online

### Current Agent Town role
- bring the first worker online
- choose/configure a mind
- establish the agent’s immediate capability

### Best benchmarks
- **while True: learn()**
- **Autonauts**

### What to borrow
- approachable explanation of a technical system
- the feeling that the player is activating a useful helper
- simplicity before depth

### What Agent Town changes
The worker is not a toy bot.
It can later become:
- a real operator,
- a real digital worker,
- a real company memory holder,
- a portable entity that might later move to laptop/server infrastructure.

### Design rule
The player should feel:
- “my partner is waking up”

Not:
- “I’m stuck in a model settings form”

---

## 4.3 Town Hall — founding the pair

### Current Agent Town role
- human identity
- agent identity
- registration/founding ceremony
- continuation into sigil/open

### Best benchmarks
- **RPG onboarding / party-formation rituals** as a general pattern
- **Game Dev Tycoon** for early momentum
- **Big Ambitions** for grounded founder fantasy

### What to borrow
- ceremonial significance
- strong sequencing
- clear meaning for each step
- emotional sense of “we are starting something”

### What Agent Town changes
This is not only character creation.
This is the formation of the **first business pair**.

### Design rule
Town Hall should feel like:
- founding a team,
- naming the company’s first two minds,
- beginning a shared story.

Not:
- filling profile forms.

## 4.4 Sigil / Open / Create — trust and founding symbol

### Current Agent Town role
- alignment ritual
- crest/seal creation
- bridge into House

### Best benchmarks
There is no perfect direct business-game equivalent.
Closest useful patterns are:
- ritual gates in narrative games
- symbolic creation moments in crafting/founding games

### What to borrow
- a small, meaningful commitment ritual
- visible transition from “not yet a team” to “now a team”

### What Agent Town changes
This is not pure symbolism.
It is also the moment where:
- coordination is proven,
- identity becomes durable,
- house creation becomes legitimate.

### Design rule
The ritual should feel:
- brief,
- memorable,
- earned,
- foundational.

## 4.5 House — headquarters and living company shell

### Current Agent Town role
- HQ
- room shell
- operating base
- launch point for memory, workshop, tracks, trainer, experiences

### Best benchmarks
- **Software Inc.**
- **Big Ambitions**
- partially **Star Office UI** as a product-clarity reference, not as a literal game comp

### What to borrow
- HQ feeling
- spatial/room semantics
- clarity of current activity
- sense of operating from one place

### What Agent Town changes
House is more than HQ art.
It is also:
- memory substrate,
- workshop,
- mailroom,
- artifact staging area,
- company-state surface,
- later worker supervision surface.

### Design rule
The player should feel:
- “this is where our company lives.”

Not:
- “this is a miscellaneous dashboard.”

## 4.6 House Library — company memory and artifact economy

### Current Agent Town role
- note authoring
- conversation capture
- revisions
- shelves and filters
- satchels/scope sets
- public stacks
- registry preview/import/publish
- peer relays
- route sync
- local trust and safety posture

### Best benchmarks
There is no single perfect game comp.
Closest useful references are:
- **Book of Hours** for the feeling of curated knowledge spaces
- **LittleBigPlanet / Dreams / Spore** for user-created artifact sharing and remix discovery
- **Steam Workshop** as a product reference for asset/package exchange, though not a game itself

### What to borrow
- curation feeling
- discovery + collect + reuse loop
- sharing of created artifacts between users/worlds
- visible provenance and identity of artifacts

### What Agent Town changes
Library is not just collectible content.
It is:
- company memory,
- extracted business knowledge,
- reusable workflows,
- packaged helpers,
- sharable public stacks,
- possible long-term exchange surface between ZHC0s.

This is one of the strongest category breaks.

### Design rule
Library should feel like:
- the living memory of the business,
- and a workshop/discovery surface for digital artifacts.

Not:
- a glorified file browser.

## 4.7 Registry — artifact directory, market, and proof surface

### Current Agent Town role
- families/entities/claims/proofs/loadouts
- grouped discovery
- proof cards
- review queue
- public stack and package identity

### Best benchmarks
- **LittleBigPlanet / Dreams / Spore** for creation-sharing ecosystems
- **Software Inc.** loosely for product/release identity
- platform references like **Steam Workshop** or app stores for catalog behavior

### What to borrow
- browseable artifact ecosystem
- discoverability by type and trust
- identity/versioning/proof semantics
- sense of a larger world of reusable work

### What Agent Town changes
Registry is not just a content browser.
It is the place where:
- worker packages can live,
- artifacts can be versioned,
- trust can accumulate,
- reuse becomes socially and economically meaningful.

### Design rule
Registry should feel like:
- a market/discovery layer for serious reusable company assets.

Not:
- an admin database disguised as a catalog.

## 4.8 Worker packages and spawn — delegation, staffing, and multi-worker evolution

### Current Agent Town role
Observed in unmerged worker branches:
- Registry-backed worker packages
- House deployments
- share-to-friend install
- helper spawn
- supervision/state/guardrails
- later pool/offload/executor abstractions

### Best benchmarks
- **Autonauts**
- **Screeps**
- **Good Company**
- partly **Software Inc.** for role/staff semantics

### What to borrow
- delegation feels empowering
- helpers have understandable jobs
- repeated labor becomes systemized
- later specialization feels natural

### What Agent Town changes
These workers are not deterministic program blocks.
They are agents with:
- memory,
- runtime profiles,
- tools,
- trust boundaries,
- portability potential,
- shareability across Houses.

### Design rule
Workers should feel like:
- real assistants becoming colleagues,
- then teams,
- then departments.

Not:
- hidden daemon processes the player cannot understand.

## 4.9 Workshop — process design, SOPs, and build bench

### Current Agent Town role
- drafts
- config lineage
- diff/apply patterns
- save outputs to Library

### Best benchmarks
- **Good Company**
- **Factorio**
- **shapez**

### What to borrow
- process clarity
- legible bottlenecks

### What Agent Town changes

- digital workers,

Not:

## 4.10 Poker — first proving ground / first experience

### Current Agent Town role
- first strong experience lane
- season/submission/review/replay/leaderboard stack
- already explicitly designed for global users and Simplified Chinese resilience

### Best benchmarks
- **competitive ladder / proving-ground games** broadly
- internally, Poker also becomes its own benchmark for Agent Town experience quality

### What to borrow
- clear rules
- visible stakes
- strong action clarity
- replay/review loop
- progression through performance

### What Agent Town changes
Poker is not the end-state product.
It is proof that Agent Town can host serious experiences where:
- humans and agents coordinate,
- performance is judged,
- memory and review matter.

### Design rule
Treat Poker as:
- the first proving ground for the broader platform.

Not:
- the final shape of all experiences.

## 4.11 Tracks — progression, unlocking, and world expansion

### Current Agent Town role
- progression hooks
- milestone surface
- quest-like guidance

### Best benchmarks
- **Game Dev Tycoon / Game Dev Story** for pacing
- **RPG quest log** conventions broadly
- **Hades / roguelite meta-progression** very loosely for “new layers open as mastery grows”

### What to borrow
- visible next step
- earned unlocking
- world expansion through progress

### What Agent Town changes
Progress should not be fake XP.
It should represent:
- proven trust,
- proven coordination,
- proven memory,
- proven operational readiness,
- real unlocked capacity.

### Design rule
Milestones should unlock:
- rooms,
- worker capacity,
- artifact systems,
- market-facing systems,
- deeper autonomy.

The world should feel more real as the company becomes more real.

## 4.12 Pony — mailroom, dispatch, and business rail

### Current Agent Town role
- messaging/inbox/policy/friends/vault flows

### Best benchmarks
No direct tycoon-game match is clean.
Closest references are:
- mail/contract systems in persistent-world games,
- logistics/dispatch feeling from automation games,
- marketplace communication loops in trading sims.

### What to borrow
- clear inbox/dispatch semantics
- asynchronous coordination feeling
- operational rhythm

### What Agent Town changes
Pony can later become:
- internal company dispatch,
- inter-company messaging,
- customer/supplier communication,
- request/reply workflow rail,
- long-term commerce coordination layer.

### Design rule
Pony should feel like:
- the company’s mailroom and dispatch desk.

Not:
- random chat bolted onto a game.

## 5. Unmerged-branch implications for ZHC0

The current repo already hints at the later shape:

1. **Agent Library branch**
   - digital artifacts
   - trust-aware discovery
   - route-following between Houses
   - same-shell sharing and import
2. **Worker spawn branches**
   - packageable helpers
   - house deployments
   - friend sharing
   - multi-worker direction
3. **House Office branch**
   - clearer HQ / office semantics
   - readiness and briefing
4. **Poker frontend branch**
   - global, human-first experience discipline
   - Simplified Chinese resilience

This means ZHC0 should be designed now with later compatibility for:
- artifact exchange,
- worker spawning,
- office specialization,
- proving-ground experiences,
- world-scale company progression.

---

## 6. Most important category caveat

If we borrow too literally from old games, we will get:
- fake products,
- fake workers,
- fake profits,
- fake progression.

If we borrow too literally from enterprise software, we will get:
- an automation dashboard,
- not a magical world.

The right synthesis is:

1. **pacing from games**,
2. **trust and reality from operating systems**,
3. **warmth and rooms from world design**,
4. **seriousness from real business outcomes**.

---

## 7. Recommendation

Design ZHC0 against this benchmark bundle:

- **Game Dev Tycoon / Game Dev Story** — first-loop pacing
- **Software Inc.** — HQ/company depth
- **Autonauts** — delegation and helpers
- **while True: learn()** — approachable AI framing
- **Good Company** — systemized workflow growth
- **LittleBigPlanet / Dreams / Spore** — artifact sharing/discovery
- **Big Ambitions** — grounded business-in-a-world feeling

But always apply the Agent Town caveat:

> the pair is not playing at running a company.
> they are learning to build one for real.
