## Boundary Model

Use these labels consistently:

- **Editor-authored draft:** private planning/content JSON. Safe for logged-in ChatGPT/Codex-enabled users to create. No gameplay effects.
- **Reviewed model:** a human/team-reviewed proposal with a schema, source-of-truth owner, tests, and explicit migration plan. Still not gameplay unless implemented.
- **Canonical engine graph:** generated by server from Founders Plot engine/store/tool definitions and current state. This is gameplay truth.

The Engine Graph Studio should be treated as a proposal studio, not a live graph editor. Canonical graph nodes should appear only after engine/server/store/tool implementation exists and the canonical graph builder reads that implementation.

- Generated report-card visual packs and copy variants for site cards, as long as they are presentation-only.

Engine/server/tool/store needed before canonical gameplay:

- Decide whether site candidates are only derived views over `scoutReports` or a new persisted engine-owned record.

Codex-enabled user boundary:

- Safe: ask Codex to summarize, rank, tag, compare, rewrite, and illustrate report plans inside private Atlas strategy/editor fields.

## Slice 2: Settler Convoy + Second Plot Claim

Goal: convert one Scout Report into the first explicit expansion action. This is the next real gameplay milestone, but it needs the most engine work.

Editor-authored now:

- Second-plot strategy plans from a selected report: "claim Forest Ridge", "wait for another report", "farm-first river outpost".
- Draft convoy costs and requirements as `resourceGate` drafts.
- `canonicalProposal`s for `unit.SETTLER_CONVOY`, `production.EXPEDITION_BOARD.CONVOY`, `territory.claim_site`, and `settlement.second_plot.create`.
- Generated visual packs for convoy, outpost foundation, route marker, claim receipt, and second-plot card.
- Copy variants for approval prompts, claim warnings, route summaries, and post-claim receipts.
- Privacy/redaction rules for sharing a planned expansion route without exposing exact private strategy.

Engine/server/tool/store needed before canonical gameplay:

- A real claimable site state model tied to scout reports: `candidate`, `reserved`, `claiming`, `founded`, `rejected` or similar.
- A convoy unit/job definition with deterministic cost, duration, actor/approval policy, and idempotency.
- A second plot creation/store model that can coexist with the first plot and remain scoped to the owner/session.
- New authoritative routes/tools, likely narrow names such as `et.plot.prepare_convoy`, `et.plot.claim_site`, and `et.plot.found_second_plot`.
- Human approval gates for irreversible or layout/ownership-changing actions.
- Canonical receipt types for `site_claim_receipt` and `second_plot_founded`.
- Atlas canonical graph nodes generated from the new model, not from saved strategies.
- Scene/UI projection for route/convoy/founded plot that remains visual-only unless backed by engine state.

Codex-enabled user boundary:

- Safe: draft claim plans, compare reports, estimate costs, prepare copy/icons, and propose exact engine graph nodes.
- Needs review/promotion: any selected claim target, costs, statuses, approval copy, or public/shareable expansion template.
- Not allowed from editor alone: creating a second plot, reserving coordinates, consuming scout reports, minting claim receipts, or granting specialization bonuses.

Recommended acceptance tests:

- Engine unit: cannot claim without a collected Scout Report; cannot claim the same report/site twice; cannot claim without resources/approval.
- HTTP: claim/found endpoints are idempotent and reject bad actor/policy states.
- Atlas: claim nodes appear only after engine model exists; editor `canonicalProposal` for claim remains advisory before that.
- E2E: build board, collect report, start convoy, approve claim, create second plot, open Atlas, see receipts and both plots.

## Slice 4: Agent Cohort Work Orders

Goal: move from individual Foreman permissions into bounded multi-step delegation while preserving server authority and receipts.

Editor-authored now:

- Work-order templates that reference existing non-executable `et.plot.*` action refs.
- Scope descriptions: "collect ready outputs", "run one scout if affordable", "prepare HQ upgrade materials".
- Approval copy, safety labels, rate-limit copy, and rollback notes.
- Draft `resourceGate`s and `canonicalProposal`s for `work_order.collect_outputs`, `work_order.scout_once`, and `cohort.builder_logistics`.
- Strategy variants for human-run, agent-assisted, and agent-cohort paths.
- Generated cohort badges, role icons, and visual-only roster cards.

Engine/server/tool/store needed before canonical gameplay:

- A `work_orders` store model with owner, scope, allowed action set, status, policy snapshot, approvals, child idempotency keys, and receipts.
- A server-owned executor/scheduler that calls existing gameplay actions under policy, not arbitrary editor JSON.
- Hard caps: per-hour actions, per-work-order actions, max resource spend, allowed building IDs, allowed job kinds, and emergency pause.
- New tools/routes such as `et.plot.create_work_order`, `et.plot.approve_work_order`, `et.plot.cancel_work_order`, and read-only work-order status.
- Receipt chaining from work order to every child gameplay mutation.
- Debug visibility in OpenClaw Lite worker traffic and Founders Plot UI.

Codex-enabled user boundary:

- Safe: draft templates, propose scopes, write approval language, and simulate/explain blockers from current Atlas read model.
- Needs review/promotion: any template that becomes selectable by real users, any default cap, and every executor action set.
- Not allowed from editor alone: running a work order, enabling policies, approving itself, minting receipts, or executing child `et.plot.*` calls.

Recommended acceptance tests:

- No work order can execute an action that the current `et.plot.*` tool would reject directly.
- Child actions get unique idempotency keys and are replay-safe.
- Agent policy and emergency pause are enforced before every child action, not only at work-order creation.
- Atlas strategy saves cannot create executable work orders.

## Generated Packs Boundary

Generated Universe and visual/content packs are valuable now, but they must stay presentation-only:

- Safe now: icons, card art, local copy variants, report skins, doctrine badge concepts, convoy/outpost mood boards, Atlas layout packs.
- Needs review: public template packs, reusable strategy packs, shared/forked plans, and generated copy that explains mechanics.
- Engine required: any pack that changes costs, unlocks, resources, report traits, doctrine effects, plot topology, civic state, or action availability.

Generated packs should carry provenance, prompt, model/tool, date, author, intended surface, and `gameplayMutationPolicy: presentation_only`.

## Promotion Workflow

1. **Draft in editor**
   - User or Codex saves a private strategy step, draft gate, icon prompt, generated pack, or `canonicalProposal`.
   - Required flags: `promotionStatus: 'draft'`, `gameplayAuthority: 'strategy_editor_advisory'` for draft gates, `authorityBoundary: 'requires_engine_promotion'` for proposals.

2. **Schema lint and normalization**
   - Server normalizes editor steps.
   - Unknown requested canonical nodes must remain `future_placeholder` or `custom_note`.
   - Non-`et.plot.*` action refs are stripped; preserved `et.plot.*` refs remain non-executable.

3. **Human/team review**
   - Review gameplay purpose, player-facing copy, privacy, reversibility, balance, and risk.
   - Decide whether the proposal is content-only, planning-only, or real gameplay.

4. **Promote to reviewed model**
   - Write a small reviewed model/spec in a report or future promotion registry.
   - Include canonical IDs, state fields, route/tool names, costs, statuses, receipts, approval policy, and tests.
   - Mark proposal as `needs_model` only when this review exists. `needs_model` is still not canonical gameplay.

5. **Implement engine/server/store/tool authority**
   - Add engine rules, store schema/migration, route/tool handlers, idempotency, policy/approval checks, public summary behavior, scene projection, and UI.
   - The implementation is the source of truth, not the editor draft.

6. **Compile canonical Atlas graph**
   - Extend `buildCanonicalAtlasGraph` or its helpers to read the new engine model.
   - Emit canonical nodes, edges, availability, action refs, and receipt refs.
   - Action refs remain `executableByAtlas: false` unless a separate reviewed execution surface is intentionally built.

7. **Back-link drafts**
   - Add a migration or normalized reference so older draft proposals can point at the promoted canonical node.
   - Change proposal status to `canonical` only after the canonical graph emits the node from engine truth.

8. **Release with tests**
   - Preserve existing no-mutation tests for editor routes.
   - Add engine/HTTP/e2e tests for the new gameplay route.
   - Add Atlas tests proving the node appears only when canonical implementation exists.

## Risks And Tests

Key risks:

- **Boundary drift:** users see a polished Atlas proposal and assume it is playable. Mitigation: labels, statuses, and tests must distinguish draft/proposal/future from canonical.
- **Stale horizon copy:** HQ6 still says Expedition Board even though Expedition Board is now HQ3 gameplay. Mitigation: retitle future horizon before the next product pass.
- **Editor mutation leak:** strategy/icon/proposal saves accidentally mutate plot state. Mitigation: compare `gameplayStableHash`, event count, inventory, HQ, buildings, jobs, policies, approvals, and scout reports before/after every editor route.
- **Action ref misuse:** saved strategies contain tool refs that a worker later treats as executable. Mitigation: keep `executable: false` and `executableByAtlas: false`; add worker tests that refuse to execute strategy action refs.
- **Generated pack rule drift:** visual packs imply different costs or abilities than engine truth. Mitigation: generated packs must be presentation-only and reviewed before public use.
- **Promotion bypass:** a proposal is added to canonical Atlas without server/store/tool support. Mitigation: canonical graph tests should assert every canonical gameplay node maps to an engine rule, store state, route/tool, or receipt source.
- **Second-plot irreversibility:** claims create ownership/state that is hard to undo. Mitigation: explicit approval, idempotency, receipt, and reject/rollback states before launch.
- **Work-order runaway:** cohort execution chains actions without fresh policy checks. Mitigation: check policy, caps, and emergency pause before every child action.

Minimum test suite to keep:

- Editor HTTP: icon draft, strategy save, strategy select, draft gate, and canonical proposal preserve gameplay stable hash and event count.
- Editor contract: unknown canonical IDs downgrade to `future_placeholder` or `custom_note`.
- Atlas canonical graph: canonical nodes are generated from engine defs/state and action refs are non-executable.
- Scout Report regression: board construction, `SCOUT` queue, report-ready output, collection, persistence, public summary count, Atlas receipt node, and receipt refs.
- Scene regression: scout actor/report-ready cue remains visual-only.
- Future slice tests: for each promoted feature, add engine unit, HTTP, Atlas, and Playwright coverage before calling it gameplay.
